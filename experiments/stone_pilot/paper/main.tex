\title{Do the Marks Survive the Pipeline? An Empirical Study of AI Code Watermark Survival Under Ordinary Software Development Operations}

\author{Anonymous Authors}

\begin{abstract}
AI-generated code is increasingly used in software development, motivating techniques that can identify whether code originated from a language model. Code watermarking has been proposed as one such approach, by embedding a detectable statistical signal into generated code. However, generated code is rarely preserved in its original form: developers routinely rename variables, format code, remove or add code, restructure programs, and apply other software development operations. It is therefore unclear whether watermarks that are detectable immediately after generation remain detectable after ordinary software transformations.

In this work, we empirically evaluate nine published AI-code watermarking schemes under 22 individual mutation operations and under a nine-step simulated software development lifecycle (agent edits, code review, continuous-integration formatting and linting, squash merge, and release packaging), applied to Python functions generated for a real open-source repository. We find that watermark survival depends heavily on both the specific scheme and the specific operation, that survival is dominated by the strength of the watermark signal at generation time rather than by the semantic content of a given edit, and that a large share of the damage attributed to individual editing operations in an earlier round of this study was in fact caused by an incidental implementation detail --- whole-file reserialization through Python's \texttt{ast.unparse()} --- rather than by the edits themselves. Once that confound is controlled for, one scheme (KGW) loses 81 percentage points of end-to-end survival when the pipeline reserializes the file compared to when the same edits are applied as in-place text patches, while a second scheme (STONE) loses only 9 points, indicating that robustness to ordinary tooling is itself a design property that varies sharply across schemes. Five of the nine schemes we attempted never produced a detectable watermark at all on the small (164M-parameter) code model used for generation, which we identify as a boundary condition on our results rather than a property of the schemes. We release our benchmark harness, mutation corpus, and full result set.
\end{abstract}

\section{Introduction}

Large language models (LLMs) are increasingly being used to generate source code, creating a need for techniques that can identify whether a piece of code was generated by an AI model. One proposed answer is code watermarking: during generation, the sampling procedure is biased in a way that is statistically detectable by a party who knows the watermarking key, but that is intended to be imperceptible to a human reader and to leave the code's behavior unchanged. A family of such schemes has been proposed for natural-language text \cite{kirchenbauer2023watermark, zhao2023unigram, hu2023unbiased, wu2023dipmark, gumbel2023, dathathri2024synthid} and adapted, or purpose-built, for source code \cite{lee2023sweet}.

Watermarking schemes are almost always evaluated on the text or code exactly as it left the model. Real code does not stay that way. Between the moment an LLM emits a function and the moment that function ships in a release, the code is typically renamed by a human reviewer, reformatted by an automatic style tool, linted and auto-fixed by continuous integration (CI), merged into a shared history (often via a squash merge that rewrites the commit itself), and packaged for distribution. Each of these is an entirely ordinary, non-adversarial operation: nobody involved is trying to remove the watermark. If a watermark cannot survive this pipeline, then watermark-based provenance claims about code that has been through a normal engineering workflow --- which is to say, essentially all code that is used for anything --- are unreliable by default, independent of whether anyone ever mounts a deliberate attack.

This raises the question we investigate: \textbf{what happens to an AI-code watermark when the generated code goes through the ordinary operations of a software development lifecycle, not a deliberate attack?} We study this empirically. We select a broad set of published watermarking schemes spanning several design families (entropy-gated, distortion-free, static and hash-chained green-list, and a production system), generate Python code with each, and subject the generated code to (a) 22 individual mutation operations drawn from version control, code review, refactoring, and packaging, and (b) a nine-step chain intended to resemble one realistic pass of a function through review, CI, and release, with detection checked after every step rather than only at the end.

A first round of this study, run at small sample sizes, appeared to show that a single operation (adding type hints) destroyed the watermark in essentially every run, for every scheme, and that only a small minority of runs retained a detectable watermark by the end of the pipeline. A larger, repeated run of the same pipeline did not reproduce either finding at the same magnitude, and a subsequent controlled experiment showed that the apparent damage from ``adding type hints'' was overwhelmingly attributable to an implementation detail shared by that operation and several others: all of them reserialize the entire file from its parsed abstract syntax tree (\texttt{ast.unparse()}), discarding the file's original formatting in the process, rather than editing the file's text in place. When the identical edits are applied as targeted, minimal text patches instead, most of the lost signal is recovered, though not all of it, and the size of the recovery differs sharply by scheme. We report this correction as a central part of the paper's contribution, because it changes the practical guidance: the primary threat to watermark survival in an ordinary pipeline may be tooling that happens to reserialize source files --- a property that has nothing to do with the semantic content of the edit being made --- rather than any specific editing operation.

Concretely, this paper makes the following contributions:
\begin{itemize}
    \item An open benchmark harness that applies 22 individual operations and a nine-step lifecycle chain to code watermarked with nine published schemes, with detection re-checked after every step rather than only at the end.
    \item An empirical finding that watermark survival under ordinary development operations is dominated by (a) the strength of the watermark signal at generation time and (b) whether the operation reserializes the source file, rather than by the specific semantic content of the edit.
    \item A demonstration, via a controlled ablation, that a scheme's tolerance to whole-file reserialization is itself scheme-dependent and large in magnitude: one scheme in our study loses 81 percentage points of survival to reserialization where a second loses 9.
    \item A worked example of how small-sample pilot results in this space can be misleading, including a documented case where two implementation defects (pseudo-replication from a collapsed generation distribution, and a randomness seed that was not actually stable across runs) produced a result that did not replicate.
\end{itemize}


\section{Background and Motivation}

\subsection{LLM watermarking}
Text watermarking schemes for autoregressive language models generally work by biasing the model's next-token distribution using a pseudorandom function of the preceding tokens (a hash-chained or fixed ``green list'' of preferred vocabulary items), or by using a modified sampling procedure whose output distribution is provably close to the unmodified one while still being statistically detectable given the key. A detector recomputes the same green list or sampling correspondence over a candidate text and computes a test statistic (commonly a z-score against a null hypothesis of un-watermarked text) or a p-value; if the statistic exceeds a threshold, the text is classified as watermarked.

\subsection{Code as a watermarking substrate}
Source code differs from natural language in ways that matter for watermarking. Code has a rigid grammar, so biasing arbitrary tokens can change program behavior or break parseability; several schemes therefore restrict biasing to non-syntax or high-entropy positions. Code is also, in practice, subjected to a battery of automated and semi-automated transformations that natural-language text is not: formatters, linters, refactoring tools, and build systems that routinely rewrite source files byte-for-byte without any human reviewing every changed character. This makes code an unusually harsh environment for a watermark to survive in, and one whose stress conditions --- an autoformatter, not an adversary --- are qualitatively different from the removal attacks (paraphrasing, back-translation) considered in most watermark-robustness literature for natural-language text.

\subsection{Why an ordinary pipeline, not an attack}
Existing robustness evaluations of text and code watermarks typically model an adversary who is trying to remove the watermark while preserving semantics, and report survival under paraphrase attacks, translation round-trips, or synonym substitution. We instead model a pipeline with no adversarial intent at all: a human accepts an AI suggestion, requests a rename, an autoformatter runs in CI, the branch is squash-merged, and the package is built for release. If a watermark does not survive this pipeline, then the practical reliability of a watermark-based provenance claim for real, deployed code is in question regardless of whether an attacker ever gets involved --- which is a strictly weaker (and, we argue, prior) condition than adversarial robustness, and one that has received comparatively little empirical attention.


\section{Related Work}

\textbf{Text watermarking.} Kirchenbauer et al. \cite{kirchenbauer2023watermark} (KGW) introduced the green-list logit-bias scheme this paper builds several code-specific variants on top of, along with a z-score detector. Zhao et al. \cite{zhao2023unigram} propose a fixed (non-hash-chained) green list, trading some unforgeability for robustness to edits that change local context. Hu et al. \cite{hu2023unbiased} and Wu et al. \cite{wu2023dipmark} propose distortion-free schemes that reweight the sampling distribution rather than adding an additive bias, so that the marginal output distribution is unchanged in expectation. Kuditipudi et al. \cite{gumbel2023} describe a family of distortion-free samplers including permute-and-flip and Gumbel-based constructions. Dathathri et al. \cite{dathathri2024synthid} describe SynthID-Text, a production system deployed at scale by Google DeepMind.

\textbf{Code watermarking.} Lee et al. \cite{lee2023sweet} (SWEET) adapt the green-list approach to code by gating the bias on token-level entropy, watermarking only positions where the model is uncertain (and therefore less likely to have its correctness constrained by syntax). STONE, the syntax-aware scheme central to this study, extends this idea by identifying non-syntax tokens directly from the target grammar rather than from entropy alone, and EWD extends KGW with an entropy-weighted detector rather than an entropy-gated embedder. CodeIP \cite{lu2024codeip} and SrcMarker \cite{yang2024srcmarker} take a different approach entirely, encoding a multi-bit message via code transformations rather than a single detectable green-list signal; we discuss in Section~\ref{sec:threats} why these are not included in our comparison.

\textbf{Watermark robustness evaluation.} Prior robustness studies for text watermarks generally evaluate against paraphrasing attacks, translation round-trips, and token-substitution attacks carried out by an adversary attempting removal. To our knowledge, no prior empirical study evaluates code watermark survival specifically against the ordinary, non-adversarial operations of a software development lifecycle --- rename, reformat, lint-autofix, squash-merge, and package build --- applied in a realistic sequence with detection re-checked at every step. This is the gap this paper addresses.


\section{Research Questions}

\begin{itemize}
    \item \textbf{RQ1:} How does the detectability of an AI-code watermark change after individual, non-adversarial software development operations (version-control operations, code review edits, refactoring, and packaging), and does this vary by watermarking scheme?
    \item \textbf{RQ2:} How does watermark detectability degrade cumulatively across a realistic sequence of such operations (a simulated development lifecycle from generation to release), as opposed to any single operation in isolation?
    \item \textbf{RQ3:} To what extent is observed signal loss attributable to the semantic content of an editing operation (e.g., the specific tokens an edit introduces) as opposed to incidental implementation properties of how that edit is applied (specifically, whole-file reserialization)?
\end{itemize}


\section{Approach}

\subsection{System Design}

We built a mutation-survival harness with four layers: (1) a \emph{scheme layer} that wraps nine published watermarking implementations behind a common \texttt{generate\_watermarked\_text} / \texttt{detect\_watermark} interface, drawn from two vendored codebases that cannot be imported into the same Python process (Section~\ref{sec:impl}); (2) a \emph{mutation layer} of 22 individual operations spanning version-control history operations, source-level edits, packaging operations, and agent-style rewrites, plus a set of human-sourced variants that draw their injected content (identifiers, comments, exception types, docstrings, type annotations) verbatim from a real codebase rather than generating it synthetically, so that these mutations cannot themselves be mistaken for AI-authored text; (3) a \emph{lifecycle driver} that chains a subset of these operations into one realistic order --- agent adds type hints, agent adds a docstring, reviewer requests a targeted patch, reviewer renames an identifier, reviewer adds a comment, CI reformats, CI auto-fixes lint, the branch is squash-merged, and the package is built into a real wheel --- and re-checks detection after every step, not only at the end; and (4) an \emph{analysis layer} that classifies each observed outcome (retained, silently lost, lost-and-surfaced by a build/parse failure, spuriously gained, never emitted at baseline, or destroyed with no source available to check) and computes retention statistics with the appropriate unit of analysis, discussed further in Section~\ref{sec:eval-metrics}.

A late addition to this design, introduced after an initial round of experiments identified a confound (Section~\ref{sec:discussion}), is a \emph{reserialization control}: for the operations most implicated in signal loss, we implemented a second, text-patch version of the same edit that inserts the identical content at AST-reported source positions using Python's \texttt{tokenize} module, rather than reparsing and reprinting the whole file with \texttt{ast.unparse()}. Both versions are seeded from the same pseudorandom draw and are checked, for every generated sample, to produce byte-for-byte the same program when parsed (verified via AST-dump equality), so that the only difference between the two conditions is whether the file was reserialized, not what the edit changed.

\subsection{Implementation}
\label{sec:impl}

We evaluate nine watermarking schemes across two vendored implementation families that cannot coexist in a single Python process because both define colliding top-level package names; every run therefore uses exactly one scheme per process. Family 1 (forked from an existing STONE-watermarking codebase) provides STONE (a syntax-aware green-list scheme that biases only non-syntax tokens), KGW (the original full-token green-list bias, used here as the code-agnostic baseline), SWEET (entropy-gated biasing), and EWD (KGW's embedding with an entropy-weighted detector). Family 2 (forked from the MarkLLM library) provides Unigram (a static, non-hash-chained green list), Unbiased and DiPmark (distortion-free schemes with p-value-based detection), SynthID-Text (Google DeepMind's mean-scoring detector variant), and a permute-and-flip sampler (PF). One further scheme with a published reference implementation, EXPGumbel, was investigated and excluded on concrete grounds (a $\sim$19\,GB initialization-time table allocation for our tokenizer's vocabulary size, confirmed by direct out-of-memory failure); two multi-bit message-encoding schemes, SrcMarker and CodeIP, were excluded because they answer a different question (message decoding rather than green-list-style binary detection) and, in SrcMarker's case, because no trained checkpoint or Python-grammar support is available.

All schemes generate from \texttt{bigcode/tiny\_starcoder\_py} \cite{starcoder}, a 164M-parameter code model, run on CPU. Generation prompts are docstring-led Python function signatures modeled on real utility functions from lutris/lutris \cite{lutris}, an open-source Python game-launcher project that also supplies the source corpus (identifiers, comments, exception types, docstring openers, and type annotations) mined for the human-sourced mutation operations, so that those operations' injected content is never itself model-generated. \texttt{delta=4.0} (the green-list logit bias strength) is shared across the schemes where it applies; detection uses each scheme's own reported test statistic and a z-score (or p-value) threshold corresponding to $p<0.05$ under the scheme's null model.


\section{Evaluation}

\subsection{Experimental Setup}

Two evaluation designs are used. The \emph{independent-operation battery} applies each of the 22 mutation operations separately to a freshly generated, freshly watermarked baseline and checks detection once, for each of the nine schemes (sample sizes per scheme constrained by which schemes produce a detectable baseline at all; see Section~\ref{sec:threats}). The \emph{lifecycle chain} applies the nine-step sequence described in Section~4.1 to the same generated function, cumulatively, re-checking detection after every step; this was run for STONE and KGW (the two schemes that reliably produce a detectable baseline on our generation model) at $n=25$ attempts under a single prompt, and subsequently re-run at $n=25$ attempts spread across five distinct prompts to reduce a pseudo-replication problem identified in the single-prompt run (Section~\ref{sec:discussion}). The remaining seven schemes were run through the same lifecycle chain at $n=5$ attempts each. A separate, tokenizer-only (no model-load) ablation replays saved baseline generations through the lifecycle's text-only steps under many random draws of the injected edit content, and through the reserialization-vs-text-patch control described in Section~4.1, allowing many more repetitions than a model-load-bound run would permit. Because the two vendored scheme families cannot coexist in one Python process (Section~\ref{sec:impl}), every run evaluates exactly one scheme per process.

\subsection{Evaluation Metrics}
\label{sec:eval-metrics}

We report, for each scheme and (set of) operations: (a) the \emph{retention rate}, the fraction of runs with a usable baseline (i.e., the watermark was actually detected before any mutation) in which the watermark remains detected after the operation; (b) for the lifecycle chain, the \emph{never-broke rate} (detected at every intermediate step) and the \emph{end-retained rate} (detected only at the final step), reported separately because they differ substantially (Section~\ref{sec:results}); (c) the \emph{first-break operation}, i.e., which step in the chain first produces a non-detection, for runs that do eventually lose the watermark; and (d) for the reserialization control, the \emph{signal-kept ratio}, the post-operation detection statistic as a fraction of the pre-operation baseline statistic, which normalizes for the fact that baselines vary substantially in strength. Runs whose baseline watermark was never detected in the first place are excluded from retention statistics and reported separately as \emph{baseline-never-emitted}, rather than being scored as a loss; this matters because five of the nine schemes in our study frequently or always fall into this category on our generation model (Section~\ref{sec:threats}). Where a chain is repeated under many random draws of injected content, we treat each distinct \emph{baseline generation}, not each run, as the unit of analysis, because a collapsed generation distribution can otherwise make identical outputs masquerade as independent samples (Section~\ref{sec:discussion}); confidence intervals are computed by bootstrap resampling over distinct baselines.


\section{Results}
\label{sec:results}

\subsection{Baseline embedding is scheme-dependent}
Of the nine schemes attempted, only STONE and KGW reliably produced a detectable baseline watermark on \texttt{tiny\_starcoder\_py}. EWD and DIP produced one detectable baseline each out of five attempts; SWEET, Unigram, Unbiased, SynthID, and PF produced none across 25 combined attempts. This spans entropy-gated, static-list, distortion-free, and production-system designs, which we take as evidence of a property of the small, low-entropy generation model rather than of any single embedding mechanism (Section~\ref{sec:threats}).

\subsection{Cumulative survival through the lifecycle chain}
In the single-prompt $n=25$ run, STONE's baseline was detected in 25/25 attempts but collapsed onto only 9 distinct generations (17 of 25 runs were a byte-identical 244-character completion, with baseline $z=4.71$, just above the $z=4.0$ detection threshold); KGW's baseline was detected in 18/25 attempts, all 18 distinct. Both schemes broke most often at the chain's first step (STONE 21/25; KGW 12/18), with KGW also breaking at the rename step (3/18) and the CI-format step (1/18). Checking only the final, released artifact substantially overstated survival relative to checking every step: STONE was detected at every single step in only 4/25 runs (16\%) but was detected at the final artifact in 23/25 runs (92\%); scores typically dropped sharply at the first step and partially recovered over the following steps, a pattern we could not fully explain (Section~\ref{sec:discussion}). KGW showed no such recovery, remaining at 2/18 (11\%) both mid-chain and at the end. Re-running the five saved baseline generations under 60 random draws each of the injected edit content showed that this as-run outcome depended heavily on baseline strength: baselines with $z>9$ were retained at the chain's end in 98--100\% of draws, while the dominant $z=4.71$ baseline was retained in only 70\% of draws and never broke in only 10\%.

\subsection{The reserialization control}
Re-implementing the type-hint-insertion step as an in-place text patch, verified to produce an AST-identical program to the original \texttt{ast.unparse()}-based version on every draw, isolated how much of the first-step loss was attributable to the annotations themselves versus to the whole-file reserialization the original implementation performed incidentally. Averaged over 13 distinct STONE and 17 distinct KGW baselines with 30 random draws each: STONE retained 59\% of its baseline signal through the reserializing version of the step versus 81\% through the text-patch version; KGW retained 41\% versus 90\%. Extending this control across the full nine-step chain (20 draws per baseline, both a fully reserializing chain and an all-text-patch chain, replayed tokenizer-only against saved baselines so that model inference was not a bottleneck): KGW's end-of-chain detection rate rose from 4\% [95\% bootstrap CI 1--8\%] under the reserializing chain to 65\% [46--82\%] under the text-patch chain; STONE's rose from 84\% [67--97\%] to 92\% [78--99\%]. Normalizing for baseline strength (end-of-chain statistic divided by baseline statistic), STONE retained 68\% [58--78\%] of its signal through the reserializing chain against KGW's 19\% [12--27\%], a gap that persisted when we checked whether it was simply a byproduct of STONE's baselines being stronger on average (within-scheme correlation between baseline strength and retained fraction was $r=-0.06$ for KGW, i.e., not headroom-driven). The order in which the CI steps (lint-autofix, format) were applied, and whether the injected edit content was drawn from a second, independent source-code corpus (Flask rather than Lutris), did not materially change these results.


\section{Discussion}
\label{sec:discussion}

\textbf{Reserialization, not editing intent, is the primary hazard.} The central practical implication of Section~\ref{sec:results} is that the mechanism by which an edit is applied matters more, in our data, than what the edit semantically changes. An agent or tool that reparses and reprints an entire file --- a common implementation pattern for AST-based refactoring tools, and one we used ourselves for several mutation operations before we identified the confound --- destroys far more watermark signal than the same edit applied as a minimal, in-place text change, and the size of that gap is itself scheme-dependent (9 points for STONE, 81 points for KGW in the isolated first-step control). This suggests a concrete, actionable design lever for anyone deploying code watermarking in practice: preferring text-patch-based tooling over whole-file-reprint tooling in the pipeline stages closest to generation may materially improve real-world watermark survival, independent of which watermarking scheme is used.

\textbf{A worked example of a non-replicating pilot result.} An earlier, small-sample ($n=5$) version of the lifecycle experiment reported here appeared to show that the type-hint step broke the watermark in 100\% of runs for every scheme with zero exceptions, that only around 20\% of runs survived the full chain for both STONE and KGW, and that this recovery was attributable to a Windows-specific line-ending conversion during packaging. None of these three claims survived a larger ($n=25$), repeated run: the first-step break rate was 84\% and 67\% rather than 100\%; end-of-chain survival was 92\% for STONE and 11\% for KGW, not $\sim$20\% for both; and the packaging step was found to flip zero individual retained/lost outcomes across 43 runs, ruling it out as an explanation. Tracing the disagreement between the pilot and the larger run identified two concrete defects: (1) the small pilot's five runs were not five independent samples, because the generation model's output distribution had partially collapsed onto a small number of distinct completions (a form of pseudo-replication that was not apparent until the larger run's distinct-generation count was examined directly), and (2) the pseudorandom seed used to draw injected edit content was derived from Python's built-in \texttt{hash()} function, which is randomized per interpreter process by default and was therefore not actually stable across separate runs of the harness, despite having been documented as deterministic. We report this not as a minor erratum but as a methodological point in its own right: small-sample robustness claims in this literature should be treated with real caution, and we recommend that future work in this space explicitly check for output-distribution collapse in the generation model before treating repeated generations as independent samples.

\textbf{Baseline strength dominates survival.} Across both the independent-operation and lifecycle results, the strength of the watermark signal at generation time (proportional to the length and lexical diversity of the generated function, in our data) was the single strongest predictor of whether that signal survived any given operation. This has a direct implication for how watermark robustness should be reported: a survival rate measured on one distribution of generation lengths is not necessarily informative about survival on a different distribution, and robustness claims should specify the baseline-strength regime under which they were measured.

\textbf{The recovery phenomenon is only partially explained.} We observed, particularly for STONE, that the detection statistic often dropped sharply at the first (reserializing) chain step and then partially recovered over the following CI and merge steps. A candidate mechanism is that the automatic code formatter used in our CI-format step (\texttt{ruff format}) rewrites reserialized code back toward a canonical style closer to what the generation model originally produced, partially undoing the reserialization's damage; a direct test found that formatting a reserialized file produced output byte-identical to formatting the unreserialized original in 4 of 13 STONE baselines and 0 of 17 KGW baselines. This is consistent with, but does not establish, that mechanism, and we report the recovery phenomenon as an open question rather than a settled finding.


\section{Threats to Validity}
\label{sec:threats}

\subsection{Internal Validity}
The lifecycle chain's step order (agent edits, then review, then CI, then merge, then release) is hand-designed to be plausible rather than mined from observed practice; a separate analysis of 281 job-step sequences drawn from the CI workflow configurations of 20 real Python repositories found that our chosen order for the CI sub-sequence (format before lint-autofix) was in fact the minority ordering (15 of 44 observed orderings, versus 29 for the reverse), though re-running the chain with both orderings produced no material difference in outcome. The single-prompt lifecycle run exhibited pseudo-replication for STONE (9 distinct generations underlying 25 nominal runs); we partially mitigated this with a five-prompt re-run (13 distinct STONE baselines, 17 distinct KGW baselines) but did not eliminate it, and all reported confidence intervals treat the distinct baseline, not the nominal run, as the unit of analysis. A pseudorandom-seed defect (Section~\ref{sec:discussion}) affected all mutation content drawn before it was identified and fixed; affected historical results were not regenerated, only superseded by re-runs under the corrected seed.

\subsection{External Validity}
All generation was performed with a single 164M-parameter model on a single host repository's prompt style; five of the nine schemes in our study never produced a detectable baseline watermark on this model at all, which bounds our results to the subset of schemes and settings for which detection was possible in the first place and leaves those five schemes' robustness properties untested here. The injected content for human-sourced mutation operations was drawn from two real source repositories (Lutris and, as a robustness check, Flask); both are Python projects, and no other language was evaluated. The green-list bias strength (\texttt{delta=4.0}) is shared across the applicable schemes for comparability but exceeds at least one scheme's published default configuration, which likely inflates absolute survival rates relative to schemes' recommended production settings; this affects all schemes using that parameter equally and should not bias comparisons between them, but no result here should be read as a general robustness claim at each scheme's own recommended settings.

\subsection{Construct Validity}
We measure watermark ``survival'' as a binary threshold classification (test statistic above or below a fixed detection threshold), which is the standard operationalization in this literature but discards information about the magnitude of remaining signal; we partially address this with the signal-kept-ratio metric (Section~\ref{sec:eval-metrics}) in the reserialization control. Our mutation operations are intended to represent realistic development actions, but several (notably the type-hint, docstring, and rename operations in their original implementation) share an incidental implementation property --- whole-file AST reserialization --- that this paper's central finding shows to be a major independent driver of the outcome; readers should treat operation-level results from before this control was introduced as measuring reserialization-plus-edit-content jointly, not the edit in isolation, unless the text-patch variant was used.

\subsection{Conclusion Validity}
We did not evaluate any generation model larger than the 164M-parameter model used throughout; this is a plausible direct cause of the baseline-embedding failures reported in Section~\ref{sec:results} and leaves open whether those five schemes would embed reliably on a larger, higher-entropy model. We were unable to obtain a matched-baseline comparison between STONE and KGW (only two of STONE's 13 distinct baselines fall within the $z\in[4,10]$ range that most of KGW's baselines occupy), so the STONE-versus-KGW comparison in Section~\ref{sec:results}, while normalized for baseline strength, is not a fully matched experimental design. We did not have access to a Linux host for this study; a platform-dependent line-ending conversion identified during packaging (LF to CRLF via a file write that did not specify a Windows-appropriate newline mode) was fixed in the harness but not verified on a native Linux run. The four Family-2 schemes not yet run through the full 22-operation battery (Unbiased, DiPmark, SynthID, PF), and the independent-operation-battery results for all nine schemes, are infrastructure-complete but not yet executed at the time of this draft.


\section{Conclusion}

We present an empirical study of whether AI-generated code watermarks survive the ordinary, non-adversarial operations of a software development pipeline, evaluating nine published watermarking schemes across 22 individual mutation operations and a nine-step simulated lifecycle from generation through code review, continuous integration, and release packaging. We find that survival is highly scheme- and operation-dependent, that baseline signal strength at generation time is the dominant predictor of survival, and --- as our central finding --- that a substantial share of the damage attributed in an initial round of this study to a specific editing operation (adding type hints) was in fact caused by an incidental implementation property, whole-file reserialization, shared by that operation and several others; when the same edits are applied as in-place text patches instead, one scheme (KGW) recovers 61 percentage points of end-to-end survival while a second (STONE) recovers only 8, indicating that tolerance to reserialization is itself a scheme-dependent design property with direct practical consequences for how code-editing tools should be built if watermark survival matters. We also document, as a methodological contribution, a case in which a small-sample pilot result did not replicate at a larger sample size, and trace the disagreement to a concrete measurement defect (an unstable pseudorandom seed) and a concrete statistical defect (pseudo-replication from a collapsed generation distribution), both of which we believe are likely to recur in similarly-scaled studies in this space unless explicitly checked for. Five of nine evaluated schemes never produced a detectable watermark on the small code-generation model available to us, which we identify as an open question for future work with access to larger models, additional host repositories, and additional programming languages.
