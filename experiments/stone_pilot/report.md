# Does a Code Watermark Survive Normal Developer Work? — Plain-Language Report

**Date:** 2026-09-26 (corrected twice; the conclusions in "The big one" changed after 25-run and control experiments)
**Full technical writeup:** `RESULTS.md` in this folder. This file is the short version.

## The question

If an AI writes some code and it gets "watermarked" (a hidden signal saying
"AI wrote this"), does that signal survive the normal things that happen to
code afterward — getting reformatted, cleaned up by a linter, merged into a
branch, or packaged for release? Or does it quietly disappear?

## What we tested

- **Watermarks — four real, published schemes**, all from the same
  research codebase so they're directly comparable:
  - **STONE** (2026) — while the AI writes code, the watermark secretly nudges
    it to prefer certain words, but only "content" words (variable names,
    values). Code structure (`if`, `def`, brackets, etc.) is left alone.
  - **KGW** (Kirchenbauer et al., 2023) — the older method STONE builds on.
    Same nudging trick, but applied to *every* word, structure included.
  - **SWEET** — nudges only "surprising" words (statistically unpredictable
    ones). Didn't work well on our small test model — more below.
  - **EWD** — nudges every word like KGW, but when checking for the watermark,
    gives more weight to words that were more surprising. A "softer" version
    of SWEET's idea. Worked even worse than SWEET — more below.
  - All four use the same detector logic: check whether a piece of text
    contains more nudged words than random chance would produce.
  - We also checked two other published schemes (SrcMarker, CodeIP) for
    inclusion and ruled them out for concrete reasons, not convenience:
    SrcMarker has no ready-to-use trained model (would need training from
    scratch) and doesn't support Python at all; CodeIP uses a completely
    different detection approach that isn't a drop-in fit with the other
    four.
- **The code:** a real function generated by a small AI code model, watermarked,
  then placed inside a real open-source project — **lutris/lutris** (a Linux
  game launcher on GitHub, ~193 real "written by AI" commits and 88 releases
  already in its history, so it's a realistic host, not a toy example).
- **The "normal things that happen to code"** — 16 operations in total,
  grouped into 3 categories:
  1. **Cleanup**: auto-formatting, auto-linting, renaming variables, adding a
     stray unused line, minifying (compressing), rewriting the code's
     structure mechanically.
  2. **Git history operations**: squashing commits, rebasing, cherry-picking,
     syncing a fork.
  3. **Packaging/shipping**: zipping the source code, building a real
     installable Python package, compiling it to bytecode only.
- We repeated everything with **fresh AI-generated code each time** — 10
  attempts for STONE and for KGW, 7 for SWEET before an unrelated crash cut
  it short (below) — because a watermark detector's answer isn't perfectly
  consistent, so running once and reporting that result would be misleading.

## What we found

**1. Git operations never hurt the watermark.**
Squashing, rebasing, cherry-picking, forking — none of these ever touched the
watermark, for any scheme, every single time. That makes sense: these
operations rearrange *history*, not the code's actual text. The watermark
lives in the text, so it doesn't care about history.

**2. Shipping/packaging the code is fine — unless you strip the source.**
Zipping the source or building a real installable package: watermark
survives every time. But if the code is compiled down to bytecode and only
the bytecode ships (no readable source left) — the watermark is gone,
completely, for every scheme, every time. Not "hard to detect" —
**impossible to check at all**, because there's no text left to read.

**3. This is the interesting part — STONE and KGW disagree on what breaks them.**

| Operation | STONE (skips code structure) | KGW (touches everything) |
|---|---|---|
| Renaming variables | ✅ survives 10/10 | ❌ breaks 0/7 |
| Minifying (compressing) | ✅ survives 9/10 | ❌ breaks 0/7 |
| Auto-formatting | ⚠️ survives 4/10 | ✅ survives 7/7 |
| Rewriting code structure | ❌ survives 1/10 | ⚠️ survives 3/7 |

(KGW's denominator is 7, not 10 — 3 of its 10 attempts never produced a
detectable watermark to begin with and were excluded rather than counted as
failures; see the note on SWEET below for why we handle this consistently.)

**This flips depending on the scheme.** STONE shrugs off variable renaming
and minifying because it never put its watermark on those kinds of words in
the first place. KGW, which marks *everything* including code structure,
gets hurt badly by exactly those same operations, because renaming and
minifying disturb structural tokens KGW was counting on. Auto-formatting
(which mostly changes spacing/line breaks) cuts the other way — it hurts
STONE more than KGW.

Both schemes ran with identical settings — the only thing that differs
between them is *which words each one chooses to nudge*. That's what makes
this comparison meaningful rather than just "two different numbers."

**Plain-English takeaway: which watermarking method is "safer" depends
entirely on what the code will go through next.** There's no universally
robust scheme in this test — each one has a different weak spot, and the
weak spot lines up with *what the scheme chose to watermark*.

**4. Two schemes (SWEET and EWD) mostly or entirely didn't work on our small
test model — and the "softer" one was worse, not better.**
SWEET only watermarks "surprising" words. Our small AI model was too
predictable/repetitive when writing code, so SWEET rarely found enough
surprising words to hide anything in — the watermark frequently failed to
embed before any mutation even happened. Of 8 clean attempts, 7 never produced
a detectable watermark, leaving 1 usable data point.

We then tried EWD, which was supposed to be a gentler version of the same
idea — instead of requiring a word to be "surprising enough" (SWEET's
all-or-nothing cutoff), it just gives more weight to words that are more
surprising. We expected this softer approach to fail less often. It did the
opposite: **0 of 8 attempts produced a detectable watermark at all** — worse
than SWEET. The reason makes sense once you see it: EWD compares each word's
surprise level to the *least* surprising word in that same piece of code, and
since our model's code is uniformly predictable, almost every word ends up
looking equally "unsurprising" relative to that minimum — so almost every
word gets weighted down to nearly nothing.

This is itself a useful, if negative, finding: **making an entropy-based
condition "softer" instead of "harder" does not automatically fix a
small-model compatibility problem — it can make it worse.** We kept all of
these non-embedding runs out of the mutation statistics rather than counting
them as mutation failures, since they never had anything to lose in the
first place.

**5. The 8th SWEET run crashed the program — not because of our code.**
We checked: at the moment of the crash, this machine had almost no free
memory left (well under 1% of 16 GB). We confirmed this by triggering the
same crash in isolation, with no mutation logic running at all — just a bare
watermark-generation call. A clean re-run on a machine with more memory
headroom is the next step for SWEET, not more debugging of our scripts. (One
good thing came out of the crash: we found that our results were only being
saved at the very end of the whole run, so a late crash lost everything
already completed. That's fixed now — results save after every single run.)

## Update: 5 more watermarks, and testing with realistic human edits

**5 more real watermarking methods added** (Unigram, Unbiased, DIP, SynthID —
yes, the same SynthID Google actually uses — and PF), all pulled from a second
real research codebase (same lab, same style of code, ~25 methods available).
We tried a 6th (EXPGumbel) and it turned out to need about 19 GB of memory
just to start up on our setup — a real limitation of that method's design for
a model with this many possible words, not something we did wrong. We're
being upfront that only one of the 5 new methods (Unigram) has been run
enough times yet to report real numbers; the other four are confirmed working
but not yet tested at scale — that's a time boundary, not a hidden result.

**Unigram's result is informative on its own**: it never once produced a
detectable watermark, even on the exact same short piece of code where STONE
and KGW's watermarks worked fine, using the same strength setting. Unigram
uses a "fixed list of words to prefer," while STONE and KGW recompute that
list at every word based on what came before. The fixed-list approach
apparently needs more words to build up enough evidence — which matches why
newer watermarking methods moved away from the fixed-list approach in the
first place.

**We also built a way to test more realistic human-style edits**, directly
addressing a fair question you raised earlier in this project: since an AI
(me) was writing the code that introduces these test edits, could that bias
the results? Our fix: every word or phrase these new edits insert — variable
names, comments, error-handling types — is copied exactly from real code
written by real humans (we scanned Lutris's actual codebase and pulled 3,326
real variable names, 757 real comments, and 36 real exception types). The
computer picks which real word to use, but it never invents a new one. Three
of the six new edit types (splitting an expression into a variable, converting
to a guard clause, reordering two lines) don't insert any words at all — they
just rearrange code that's already there.

**Two things we found from running these:**
- Renaming variables to *real, natural* names broke STONE's watermark more
  often than renaming to short placeholder names like `_v1`/`_v2` did (2 out
  of 5 vs. 5 out of 5 surviving). That's a small sample so we're not
  overclaiming it, but it makes sense: natural names vary a lot in length and
  spelling, while placeholder names are all short and similar, so natural
  names likely disturb more of what the watermark depends on.
- Three of our new "human-style" edits (extract variable, guard clause,
  reorder lines) broke the watermark at almost exactly the same rate as our
  earlier "rewrite the code's structure mechanically" test. That's suspicious
  in an honest way: all four of these edits end with the same code-formatting
  step internally, so what we're measuring might be more about that shared
  formatting step than about the human-style edit itself. We're flagging this
  plainly rather than hiding it — it's a real limitation of this test that a
  future version should fix by only reformatting the part that actually
  changed.

## The big one: what happens through an entire realistic development cycle

> **Corrected twice.** A first 5-run version made claims that a 25-run rerun
> overturned (2026-09-24). Follow-up controls on 2026-09-26 then changed the
> explanation again. What follows is the current picture, then a plain list of
> what we got wrong and when.

Everything above tests one change at a time, starting fresh from the original
watermarked code each time. Real code gets several changes in a row —
someone adds types, a reviewer asks for a tweak, CI formats it, it gets
merged, it ships. So we built a test that applies one realistic sequence of 9
steps to the *same* piece of code and checks whether the watermark still
shows up after **every step**, not just at the end: an AI agent adds type hints
→ adds a docstring → a reviewer asks for a small fix → a rename → a comment →
CI auto-formats → CI auto-fixes lint → squash-merge → package for release.

**The answer, in one sentence.** What destroys the watermark is not any
particular edit, it's tools that **rewrite the whole file from scratch** (our
test used Python's own code printer, which throws away the original spacing,
quotes and layout). The same edits made as small in-place text changes cost far
less.

**How we know.** We took the same AI-written programs and added the same type
hints two ways: (a) by rewriting the whole file, (b) by inserting just the type
hints in place and leaving every other character alone. Both produce the exact
same program. The watermark that survived:

| | Whole-file rewrite | In-place edit |
|---|---|---|
| STONE | about 59% of its strength | about 81% |
| KGW | about 41% of its strength | about 90% |

So type hints themselves barely matter; the rewrite does the damage.

**Over the whole 9-step sequence** (20 random draws of the edits on each of 13
different STONE programs and 17 different KGW programs; the "still there at the
end" figures are shares of runs):

| | Every step rewrites the file | Same edits, in place |
|---|---|---|
| STONE still detected at the end | 97% | 98% |
| KGW still detected at the end | **4%** | **65%** (range 46–82%) |

For KGW that is the whole story: 4% versus 65%. STONE mostly survives either
way, and it keeps about 68% of its original strength through the rewriting
sequence against KGW's 19%. That gap is not just STONE starting stronger — among
KGW's own runs, retention doesn't depend on how strong they started. We can't
prove a design reason from this, though STONE deliberately ignores punctuation
and layout-type tokens, which is exactly what a rewrite changes. We haven't
tested that idea.

**Things that turned out not to matter:**
- *The order of the CI steps.* Real projects (we looked at 20 well-known Python
  repositories) run "fix lint" before "format" about twice as often as the
  reverse; we had used the less common order. Testing both changed nothing.
- *Whose vocabulary the edits use.* Drawing the comments and names from a second
  real project (Flask, instead of Lutris) gave the same picture.
- *Windows line endings and packaging.* Never changed whether the watermark was
  detected in any run. (We now also fix the line-ending issue in the test code.)

**How many independent samples we really have.** With one prompt, STONE's small
AI model wrote the *same* short program in 17 of 25 runs. We now use five
different prompts, which gives 13 different STONE starting points (from 23
usable runs) and 17 for KGW, and we treat each *program*, not each run, as one
sample. It's better, not perfect.

**One thing we can only half explain.** The watermark's strength often dips at
the first rewriting step and then partly comes back after the formatter runs.
Our best guess is that the formatter writes the code back to the style the AI
originally used. That checks out exactly for 4 of 13 STONE programs and none of
the KGW ones, so it's suggestive, not settled.

**What we got wrong, and when:**
- *5-run version:* "adding type hints broke the watermark 100% of the time and
  is the most destructive change." Wrong. At 25 runs it was 84% and 67%, and on
  2026-09-26 we showed it was mostly the file rewrite, not the type hints.
- *5-run version:* "only about 1 in 5 survives the whole sequence for both
  methods." Wrong for both: it depends heavily on the method and on whether the
  tools rewrite the file. Our first runs happened to draw mostly one weak,
  very short program.
- *5-run version:* "Windows line breaks explain why the watermark came back."
  Withdrawn: they explain nothing here.
- *5-run version:* "type hints remove 52–84% of the signal." That came from
  four favorable runs picked after seeing the data.
- *Setup bug:* our edits were described as "deterministic" but weren't (the
  random choice changed each time the program started). Fixed on 2026-09-24.
- *25-run version:* it still used one prompt, so part of the "STONE lost it at
  step 1 but got it back" pattern came from that one short program.

### Where does each of the nine methods break?

We also ran the original sequence (which rewrites the file at several steps, so "step 1" below mostly means "first rewrite") for the other seven methods (5 attempts each).
Five of the nine methods never produced a working watermark on our small AI
model at all, so there was nothing to test:

| Method | Usable runs | Where it first broke |
|---|---|---|
| STONE | 25 of 25 (one prompt) | mostly step 1 (21 runs) |
| KGW | 18 of 25 (one prompt) | step 1 (12), rename (3), formatting (1) |
| EWD | 1 of 5 | step 1 (one run — too few to say anything) |
| DIP | 1 of 5 | step 1 (one run — too few to say anything) |
| SWEET, Unigram, Unbiased, SynthID, PF | 0 of 5 each | never produced a watermark to test |

The five that never worked span very different designs (a fixed word list, a
"distortion-free" design, and the one Google actually uses), so this looks
like a problem with our small model rather than with any one method. Judging
them fairly needs a larger AI model.

## Why this might matter for the bigger paper

The paper's central argument is that ordinary software operations — not
attackers — quietly destroy or manufacture claims about where code came
from. This experiment adds a concrete, testable version of that for AI code
watermarks specifically:

- It's not "watermarks are robust" or "watermarks are fragile" — it's **"a
  watermark's fragility is a mirror of its own design choice about what to
  mark,"** and different ordinary operations expose different design choices.
- A robustness number reported for one scheme, on one kind of code, cannot be
  assumed to transfer to another scheme — the STONE/KGW table above is direct
  evidence of that, not just a claim.
- Longer generated code produces a stronger baseline watermark signal, and
  that signal strength predicts survival better than the mutation itself
  does: across repeated runs, how much code the model wrote correlated with
  the watermark's starting strength at **r = 0.99** for STONE and
  **r = 0.88** for KGW (1.0 would be a perfect straight-line relationship).
  Practical meaning: **any reported survival number needs to say how much
  code it was measured on**, or it isn't comparable to another study's number.

## Honest limits (so this doesn't get overstated)

- Small sample per cell (7-10 repeated runs for STONE/KGW), one small AI model
  (164M parameters), one repository, one scheme family (all four watermarks
  come from the same published codebase, though they're genuinely different
  algorithms).
- SWEET and EWD's results are inconclusive due to the embedding-failure
  problem above — need a bigger/different model before either can be fairly
  judged on mutation robustness.
- These are single generated functions, not large realistic codebases.
- All three schemes were run with a stronger-than-typical setting (to make
  the small model's watermark reliably detectable in the first place), which
  likely makes every survival number here somewhat higher than it would be
  at the settings the original papers recommend. This affects all three
  schemes equally, so it doesn't unfairly favor one over another, but it
  means none of these numbers should be quoted as "how robust this scheme is
  in general."
